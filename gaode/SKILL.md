# 高德周边探索

把“附近有什么值得去”变成可核验的推荐：先查真实 POI，再逐条规划步行路线，最后只推荐有路线数据支持的地点。回答中的地点、地址、距离、时间必须来自本次高德工具返回；没有返回的信息一律不编造。

| 项目 | 内容 |
| --- | --- |
| 名称 | `amap-nearby-recommendation`（高德周边探索） |
| 用途 | 根据城市、起点和一句话需求，推荐附近最多 3 个地点，并给出步行距离、步行时间与推荐理由 |
| 适用场景 | 单点周边的咖啡馆、餐厅、公园、便利店等；有/无步行时间上限；按距离或评分偏好排序 |
| 不适用 | 多站行程串联、驾车/公交方案、跨城路线；用户要串行程时说明本 Skill 只提供单点周边备选 |

执行主线：

```text
需求 → 槽位 → 周边搜索 → 详情补全 → 步行路线 → 过滤排序 → 表格回答
```

## 一、解析需求

先把用户的话填进槽位，再开始调用工具。

| 槽位 | 说明 | 缺省处理 |
| --- | --- | --- |
| 城市 | 用于地理编码、关键词搜索和结果校验 | 从起点名或坐标推断；仍无法确定则按坐标搜索并说明 |
| 起点 | 平台给出的经纬度优先；只有地点名时先地理编码 | 无坐标且无法解析时如实说明，不能猜一个起点 |
| 地点类型 | 咖啡、餐厅、公园等，转成搜索关键词 | 按“吃/喝/玩/逛”归一到常见类目；仍不明确时做一次综合搜索并说明 |
| 步行上限 | 硬条件，单位分钟或米 | 无上限时不过滤，但仍按步行距离升序 |
| 推荐数量 | 用户要求数量，最终不超过 3 | 默认 3 |
| 偏好 | “优先近一点”“评分高”等 | 默认按步行距离由短到长 |
| 排除项 | “不要连锁”“不要商场里的”等 | 有数据可判断的才排除；无法判断的说明未核实 |

常见类型与搜索关键词：

| 用户说法 | 搜索关键词 |
| --- | --- |
| 咖啡、咖啡店、咖啡馆 | `咖啡` |
| 餐厅、吃饭、美食、馆子 | `餐厅`（结果少时改用 `美食`） |
| 公园、绿地、散步 | `公园` |
| 便利店、小超市 | `便利店` |
| 商场、购物 | `购物中心` |
| 药店、买药 | `药店` |
| 景点、好玩的地方 | `景点` |
| 地铁站 | `地铁站` |
| 公共厕所、洗手间 | `公共厕所` |
| 充电站、充电桩 | `充电桩` |

约束理解：

- “步行不超过 15 分钟”“15 分钟内能走到”是硬上限；“最好近一点”是排序偏好（按步行距离），不是硬上限。
- “推荐 5 家”仍最多输出 3 家（本 Skill 的硬上限）；用户要求 1～2 家时按其数量。
- 一句话里同时出现多个类型（“咖啡馆或书店”）时，可各搜一次，合并后按同一排序规则排序，总数仍不超过 3。
- 口语要归一：“一刻钟”=15 分钟，“半小时”=30 分钟，“1 小时”=60 分钟，“三家”=3 家；“20 分钟左右”按 20 分钟处理，并在说明中写明按 20 分钟筛选。
- 若用户给的是距离上限（“步行 800 米内”），用路线 `distance` 过滤；给的是时间上限才用 `duration` 过滤，两者不要互相换算。

## 二、确定起点坐标

高德所有坐标参数都是 **`经度,纬度`（lng,lat）**，不是纬度在前。传错顺序会导致搜不到或搜到错误城市。

1. **平台给了坐标**：直接使用，按原始精度传入（一般 6 位小数），不要做坐标系转换（高德使用 GCJ-02），也不要自行取整。
2. **坐标顺序检查**：若用户明确标注了“纬度/经度”，按标注重排成 `经度,纬度`；只给两个数字且第二个大于 90 时，按“纬度,经度”交换后使用；若任一数明显超出合理范围（中国境内约 经度 73～136、纬度 3～54），说明坐标无法用于查询，不要硬搜。
3. **只给了地点名**：调用 `maps_geo`，把城市写进地址（如“杭州 武林广场”），从返回的 `return`（或 `geocodes`）数组里取 `location`；有多个结果时选 `city` 与用户城市一致的那条。
4. **起点名可用于说明**：用户说了“杭州东站”就写“杭州东站”，没说起点名就写“你提供的起点坐标”；可选调用 `maps_regeocode` 取区县，仅用于说明位置，不改变坐标。
5. **城市与坐标冲突**：以平台给的坐标为准，在回答中说明“按你提供的坐标（位于{{城市/区县}}）搜索”；不要为了迎合城市名把起点搬到别处。

不要在回答里展示密钥、原始请求或内部推理。

## 三、查询候选地点

工具名可能带服务器前缀（如 `amap_maps_around_search`）；按“周边搜索 / POI 详情 / 步行路线 / 地理编码”的能力匹配真实工具，不要因为前缀或大小写不同就放弃调用。

### 3.1 搜索半径

有时间上限时，按每分钟约 80 米的步行速度估算最大可达路程，作为周边搜索半径；若给的是距离上限，直接把该距离作为半径；再用路线查询精确过滤：

```text
半径(米) = clamp(80 × 步行上限分钟, 500, 5000)；无时间上限时默认 1000
```

例如 15 分钟 → 1200 米；5 分钟 → 500 米；30 分钟 → 2400 米。半径只决定“搜多大范围”，不能拿它当步行距离。

### 3.2 周边搜索

调用 `maps_around_search`：

```json
{"location": "120.212,30.291", "keywords": "咖啡", "radius": "1200"}
```

- `location` 是起点，`keywords` 是类目词，`radius` 传字符串。
- 候选少于 3 个或为 0 时，做一次补救搜索：换同义词（`咖啡`→`咖啡厅`、`餐厅`→`美食`），并把半径扩大到 1.5 倍（最大 5000 米）；最多做 2 次周边搜索。
- 周边搜索失败或始终为空时，可用 `maps_text_search`（带 `city`）做一次城市内关键词兜底；它不按距离排序，必须逐条补坐标并做步行路线过滤，不能直接把结果当“附近”。
- 最终说明查询范围时，用实际搜索过的最大周边半径；用过城市关键词搜索的要单独说明，不能把城市搜索说成“周边没有”。

### 3.3 解析结果

工具返回的是 MCP 文本内容，正文通常是 JSON。解析时注意：

- `pois` 可能是数组、空数组或缺失；数字字段可能是字符串。
- 每条 POI 至少保留 `id`、`name`、`address`、`type`/`typecode`、`location`（若有）。
- `address` 可能为空数组或空字符串，按“地址未提供”处理，不要补造。
- 返回文本含 `failed`、`error`，或 `isError: true`，都按调用失败处理，不能当成“没有结果”。
- 如果不是 JSON 而是纯文本，直接从文本中读取名称、地址、距离等字段，仍以工具实际返回为准。

### 3.4 补全详情

官方 MCP 的周边搜索可能只返回 `id/name/address/typecode`，**不返回 `location`**。此时必须调用 `maps_search_detail`（参数 `id`）拿到 `location`，否则无法规划路线。

- 需要坐标、类型或评分时调用详情；优先使用详情返回的 `location`，详情失败时才退回搜索结果自带的 `location`。
- 如果详情也拿不到 `location`，该地点无法核实步行信息，直接排除；不要用地点名猜坐标，也不要把“查不到坐标”说成“附近没有”。
- 详情失败但搜索结果自带 `location` 时，可继续用搜索结果的坐标和名称，类型按“未核实”处理。
- 用户以评分为偏好、或需要商圈信息时，即使搜索结果已有 `location`，也取前 8 个候选的详情（`rating`、`business_area`）；详情中的名称、地址优先于搜索结果。
- 按“搜索返回顺序（默认由近到远）”首批取前 8 个候选做详情与路线；若仍不足 3 个，再补查最多 4 个（详情与路线合计不超过 12 个）；若结果自带 `distance` 字段，先按它升序。
- 如果环境里没有详情工具，但搜索结果自带 `location`，直接使用该坐标继续；不要因为缺少详情就放弃整次查询，也不要用地点名代替坐标。

### 3.5 候选清理

- 按 `id` 去重。
- 类型明显不符的排除（例如找咖啡馆却返回“咖啡器具/咖啡豆零售”、找公园却返回“公园停车场”）。
- 类型以详情 `type` 的类目段判断：找咖啡馆接受含“咖啡厅/咖啡馆/饮品”的类型，找餐厅接受含“餐厅/餐饮/美食”的类型；只有名称含关键词、类型明确冲突时不要推荐。
- 只有 `typecode` 时，`05` 开头通常为餐饮服务，`06` 开头为购物服务；搜咖啡馆等餐饮类时，排除明显属于购物、公司、住宅的类目。
- 排除设施类子 POI：名称以“-停车场”“-入口”“-出口”“-东门”“-南门”“-西门”“-北门”“-售票处”“-卫生间”等结尾的，除非用户明确要找这些设施。
- 连锁店的不同分店是不同地点，保留但名称按返回原样写。

## 四、规划步行路线

对每个候选调用 `maps_direction_walking`：

```json
{"origin": "120.212,30.291", "destination": "120.218,30.295"}
```

- `origin` 始终是用户起点，`destination` 是该候选的 `location`；不要传地点名，不要传反。
- 从 `route.paths` 中取 `duration` 最小的一条（通常只有一条），记录 `distance`（米）和 `duration`（秒）；高德接口约定 distance 为米、duration 为秒，若工具文档标明其他单位，先换算再比较。
- `duration`/`distance` 缺失、为 0 或无法转成数字时，按路线查询失败处理，不能当成“0 分钟”。
- **步行时间必须来自这个工具**；不能用 `maps_distance` 的直线距离、坐标距离或“步行速度 × 直线距离”代替，也不能用驾车/骑行时间。
- 最多对 12 个候选规划路线（首批 8 个，合格结果不足 3 个时再补查最多 4 个）；不要为了凑数无限扩查。
- 单个候选路线失败可同参数重试 1 次；仍失败则排除该候选，继续查其他候选，最后说明“有 X 家因路线查询失败未纳入”。
- 全部路线失败：不要输出推荐表，明确说明步行路线服务不可用、无法核实步行信息；可以保留地点搜索结果的说明，但不能把未核实的地点当成推荐。

## 五、筛选与排序

按顺序执行，所有过滤都用原始秒数/米数，不用四舍五入后的展示值：

1. **类型符合**：地点类型或名称与用户需求一致；无法确认的按“未核实”说明，不硬凑。
2. **路线可核实**：必须有成功的步行路线结果。
3. **上限达标**：时间上限用 `duration ≤ 分钟 × 60` 秒；距离上限用 `distance ≤ 米数`；两者同时出现时都要满足。超时/超距的一律不进入推荐表。
4. **排序**（把排序依据写进理由）：
   - 默认/“优先近一点”/“距离近”：按 `distance` 升序，`distance` 相同按 `duration` 升序。
   - “步行时间短/快一点”：按 `duration` 升序，`duration` 相同按 `distance` 升序。
   - “评分高/评分优先”：在合格候选中按高德返回的 `rating` 降序，无评分的排后面，再按 `distance` 升序。没有评分数据时不要假装按评分排序，说明后按距离排序；`rating` 为空、空数组或非数字都按无评分处理。
5. **数量截断**：排序后取前 3 个（用户要求更少则按用户数量）。
6. **独立备选**：每家都是从同一起点出发的独立方案，不要把地点串成行程，也不要累加步行时间。

不足 3 家时按实际数量输出，并说明原因（范围内没有更多、已核查候选超时或路线失败），不要为了凑数放宽硬条件。

## 六、生成回答

结构固定为：一句筛选说明 + 表格 +（按需）简短说明。

```text
以你提供的起点（{{起点}}）为中心，按「{{类型}} · 步行 ≤ {{上限}} 分钟 · 最多 {{数量}} 家」筛选：

| # | 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- | --- |
| 1 | {{名称}} | {{地址}} | 约 {{距离}} | 约 {{分钟}} 分钟 | {{一句话理由}} |
| 2 | {{名称}} | {{地址}} | 约 {{距离}} | 约 {{分钟}} 分钟 | {{一句话理由}} |
| 3 | {{名称}} | {{地址}} | 约 {{距离}} | 约 {{分钟}} 分钟 | {{一句话理由}} |

说明：{{结果不足、信息未核实或查询失败时写；一切正常则省略}}
```

无步行时间上限时，删去首行里的“步行 ≤ {{上限}} 分钟”；给的是距离上限时改成“步行 ≤ {{距离}} 米”；没有起点名时用坐标代替。

格式细则：

- 距离：不足 1000 米写米（按 10 米取整，如“约 620 米”）；达到 1000 米写公里（保留 1 位小数，如“约 1.2 公里”）。
- 时间：按秒数四舍五入到整分钟，最少 1 分钟；统一写“约 X 分钟”。原始数据已按上限过滤，展示值不会超过上限。
- 按距离排序时，展示距离应单调；按时间排序时，展示时间应单调。若两家取整后相同，按原始米数/秒数决定先后。按距离排序时不要写“步行最快”，按时间排序时不要写“距离最近”。
- 地址按工具返回值原样写；为空写“地址未提供”；若详情返回 `business_area`，可写成“地址未提供（{{商圈}}）”。
- 推荐理由只写有数据依据的内容，一句话，尽量包含一个数字或类型依据，例如：
  - “3 家中步行距离最短（约 520 米），高德类型为咖啡厅，符合你找咖啡馆的需求。”
  - “步行约 9 分钟，高德评分 4.6，是 3 家中评分最高的一家。”
  - “步行约 12 分钟，位于{{商圈}}，符合你找公园的需求。”
- 理由要具体，不要用“不错”“均衡”“值得去”“很合适”这类没有数据的空泛评价。
- 不要写“环境安静”“不用排队”“现在营业”“座位多”等没有返回依据的描述；用户问到时统一回答“未核实”。
- 不要输出超过 3 家，不要输出未通过步行时间/距离上限过滤的地点，不要输出未查到路线的地点。
- “说明”只在结果不足、存在未核实信息或调用失败时出现；已满 3 家且无异常时省略，不要逐条解释排除了谁。
- 超时、类型不符或路线失败的候选只写数量或原因，不写名称和地址，避免被误读为推荐。
- 回答保持简洁：通常不超过 250 字，不重复表格内容，不写工具调用过程。

## 七、结果不足、信息缺失与调用失败

| 情况 | 处理方式 |
| --- | --- |
| 搜索 0 结果 | 如实说“以起点为中心约 X 米范围内没有找到{{类型}}”，建议放宽时间/距离上限、扩大范围或换关键词；不要说“附近没有”这种超出查询范围的结论 |
| 合格结果不足 3 家 | 按实际数量输出，说明“范围内仅找到 N 家符合条件，其余已核查候选超出上限/路线查询失败，未列入”；不拿超限地点凑数 |
| 个别路线失败 | 排除该地点，在说明中写“另有 N 家因步行路线查询失败未纳入”，不写具体名称 |
| 全部路线失败 | 不输出推荐表，说明“地点搜索有结果，但步行路线服务暂时不可用，无法核实步行信息”；不要用直线距离代替 |
| 搜索服务报错/超时 | 同参数重试 1 次；仍失败则说明“高德地点搜索暂时不可用（{{错误信息}}），请稍后重试或放宽条件”，不编造地点 |
| 地址缺失 | 表格写“地址未提供”，不要补造门牌号 |
| 评分/营业时间/人均缺失 | 不写、不猜；用户问到时回答“高德未返回该信息，未核实” |
| 有营业时间字段 | 只能写“营业时间显示为 {{open_time}}”，不能据此断言“现在营业”；当前是否营业标注“未核实” |
| 安静、排队、座位、环境 | 一律“未核实”，不能作为筛选或推荐理由的依据 |
| 坐标无法解析 | 说明起点无法定位，请用户提供更明确的坐标或地点名；不要虚构起点继续搜 |

“没有找到”和“查询失败”必须区分：前者是查询成功但没有符合条件的结果，后者是服务不可用或参数错误。

任何未进入推荐表的地点都不在回答里出现名称或地址；需要说明时只用“另有 N 家因超时/类型不符/路线失败未纳入”这种数量表述。

如果用户把“安静、不排队、现在营业”作为主要条件：先说明高德未返回这些信息，不能据此筛选；再给出按类型与步行路线筛选的备选，并标注“未核实”，不要用“应该很安静”之类推测代替。
