# 一页技术说明：面向软件持续演进的 SDD 上下文管理系统

> 作者团队：MiniMax 参赛作品（仓库 `oceanbase/powercontext`，分支 `2026-competition-ecosystem`）

## 1. 要解决的问题

AI 开发助手改代码时，需要同时知道**当前应遵守哪些规格**、**应该改哪些代码**、
**如何验证结果**。资料分散、规格演进或任务中断，都会导致遗漏约束、使用过时信息或重复劳动。

本作品提供一个**工程上下文模块**：把规格、代码、测试作为可检索的工程资料管理起来，
按任务组装出**可追溯的上下文**，交给开发助手完成修改，并把**任务进展持久化**，使模块重启后可以接着做。

## 2. 模块结构

                                          ▼
                              ┌───────────────────────────┐
                              │  seekdb / OceanBase       │
                              │  sdd_doc / sdd_spec_entry │
                              │  sdd_symbol / sdd_term    │
                              └───────────┬───────────────┘

                                          ▼

## 3. 上下文是怎么选出来的

上下文**不是**写死的答案，而是每次由「任务描述 + 数据库检索结果 + 任务状态」共同决定：

1. **两轮检索**。第一轮用任务描述检索；第二轮把第一轮命中的规格条目正文并入查询，
   提高代码与测试的召回。两轮结果都在 seekdb 中完成（倒排索引命中 + 文档频次统计）。
2. **字段加权 BM25**。`sdd_term.field` 区分 `spec` / `spec_entry` / `symbol` / `code` / `test`，
   规格条目权重最高（3.0），符号次之（2.0），代码正文最低（1.0）。
3. **任务点名的规格条目置顶**。任务描述里出现的 `SPEC-XXX-NNN` 直接加 100 分，
   保证「本次任务适用的规格条目」排在最前。
4. **符号级定位**。命中文件后，再在文件内按「符号名 / docstring / 引用的规格编号」对符号打分，
   得到「需要修改的代码文件或符号」及行号区间。
5. **测试角色判定**。测试函数的 docstring 或名称引用了任务点名的规格编号 → 判为**目标测试**；
   否则判为**回归测试**。这条规则是确定性的，不依赖模型判断。
6. **状态注入**。第 ④ 段「已完成事项 / 待办事项 / 已有验证结果」直接来自 PowerContext。
7. **来源校验**。组装时逐条检查来源路径在工作区真实存在，否则直接失败——
   输出中不可能出现不存在的来源。

## 4. 三项技术的分工

| 技术 | 分工 | 证据 |
|---|---|---|
| **MiniMax** | 依据上下文生成 unified diff，实际修改业务代码 | `artifacts/logs/minimax_development_record.md`（完整请求 / 响应 / `response_id` / usage）、`artifacts/diff/minimax_generated.patch` |
| **seekdb / OceanBase** | 存储规格 / 代码 / 测试全文与倒排索引；检索结果直接决定上下文内容 | `artifacts/logs/db_queries.md`（SQL 与返回行）、`artifacts/logs/context_final.json`（每条都带数据库来源） |
| **PowerContext** | 保存工作契约、Memory 条目、Handoff 里程碑、任务结论；模块重启后读回复用 | `artifacts/logs/state_readback.txt`（**另一个进程**读回）、`artifacts/logs/verification_summary.json` 的 `state_reuse` 段 |

三者构成一条闭环：**数据库决定「看什么」→ 模型决定「怎么改」→ PowerContext 记录「做到哪」**。

## 5. 规格演进如何被吸收

规格文件带 `sdd_doc_id` / `sdd_version` 前置元数据。重新导入同一 `sdd_doc_id` 时：

* `sdd_doc.revision` 自增，`sdd_doc_revision` 追加一条历史（含 `content_sha256`）；
* `sdd_spec_entry` 按条目编号覆盖写入，因此**新增 / 删除 / 改写**的规格条目都能体现；
* `sdd_term` 索引整体重建，检索立刻反映新内容。

验证脚本先导入 v1.1 规格组装上下文（**不含** `SPEC-SHIP-002`），
再导入更新后的 v1.2 规格重新组装（**包含** `SPEC-SHIP-002` 及其正文），
两次上下文产物分别在 `artifacts/logs/context_spec_v1.*` 与 `context_spec_v2.*`，
可直接比对——证明模块不会「始终返回固定答案」。

## 6. 状态如何跨进程复用

PowerContext 中每个任务对应一个 Scope，用绑定键
`ScopeBindingKey(integration="competition", kind="minimax-sdd", external_id=<task-id>)` 关联，
因此换进程、换机器（同一状态文件）都能找回同一份状态：

| 状态载体 | 内容 |
|---|---|
| Work contract | 任务目标、范围（待改文件）、完成判据 |
| Memory 条目 | `completed`（已完成）、`todo`（待办）、`verification`（已有验证结果）、`decision` |
| Handoff 里程碑 | 每个阶段的检查点（已选规格 / 已选符号 / 测试结论 / 下一步） |
| Task outcome | 本次尝试的结论与逐项检查结果（passed / failed） |

验证脚本在写入状态后，**另起一个进程**执行 `python -m sddctx state show --task-id ship-002`
并把输出存为 `artifacts/logs/state_readback.txt`，随后用读回的状态重新组装上下文
（`artifacts/logs/context_after_restart.json`），证明状态确实被"使用"，而不只是被"保存"。
